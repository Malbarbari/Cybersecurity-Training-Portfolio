# Urban Sports — Cybersecurity Final Project

## Overview

**Urban Sports** is a cybersecurity final project that demonstrates a complete security assessment lifecycle in a controlled lab environment.

The project involves building and testing a deliberately vulnerable web application, performing security attacks against identified vulnerabilities, monitoring and analyzing generated logs using **Splunk SIEM**, and finally applying remediation techniques to secure the system.

The project was designed to demonstrate practical skills in:

- Vulnerability identification
- Web application penetration testing
- Attack simulation
- Log collection and analysis
- SIEM monitoring and detection
- Incident investigation
- Vulnerability remediation
- Security verification

> **Disclaimer:** This project was developed strictly for educational purposes in an isolated and authorized lab environment.

---

## Project Architecture

The lab environment consists of multiple machines connected remotely using **Tailscale VPN**.

Each team member operated their assigned machine locally while Tailscale provided secure connectivity between the systems.

### Main Components

**Vulnerable Web Server**
- Hosts the Urban Sports vulnerable web application
- Apache Web Server
- Generates Apache access/error logs
- Contains intentionally vulnerable functionality for security testing

**Attacker Machine**
- Kali Linux
- Used to perform reconnaissance and authorized attack simulations against the vulnerable application

**SIEM Machine**
- Kali Linux
- Splunk Enterprise
- Receives and analyzes logs generated during attacks
- Used to create searches and investigate suspicious activity

**Secure / Remediated Environment**
- Vulnerabilities identified during testing were fixed
- Security controls were applied
- The application was tested again after remediation

## Vulnerability Assessment

The Urban Sports application was intentionally configured with vulnerable functionality to allow the team to study realistic web security issues.

The assessment included identifying vulnerable application behavior, understanding how the vulnerability could be exploited, and observing the evidence generated by the attack.

Testing was performed only against systems belonging to the controlled project environment.

---

## Attack Simulation

The attacker machine was used to reproduce attacks against the vulnerable application.

The purpose of the attack phase was not only to demonstrate exploitation but also to generate realistic evidence that could later be investigated from the defensive side.

The attack workflow included:

1. Identifying the target.
2. Performing reconnaissance.
3. Testing vulnerable functionality.
4. Exploiting identified vulnerabilities.
5. Generating HTTP requests and system activity.
6. Reviewing the resulting logs.

---

## SIEM Monitoring with Splunk

**Splunk Enterprise** was used as the project's Security Information and Event Management (SIEM) platform.

The SIEM machine collected relevant logs from the vulnerable environment and allowed the team to search and analyze events generated during the attack simulations.

### Log Sources

The primary log sources used in the project were:

- **Apache Web Server Logs**
- **Shell History / Bash Logs**

These sources provided visibility into web requests and relevant command-line activity available within the scope of the lab.

### Apache Logs

Apache logs were used to investigate HTTP activity directed toward the vulnerable application.

They provided information such as:

- Source IP addresses
- Requested URLs
- HTTP methods
- Response codes
- Request timestamps
- Suspicious request patterns

### Shell History

Shell history provided additional visibility into commands executed on the monitored Linux environment.

This information helped correlate host activity with other events observed during the assessment.

---

## Detection & Investigation

Splunk searches were created to investigate activity generated during the attack phase.

The analysis focused on identifying suspicious patterns inside the available log sources and correlating them with known attack activity.

Example investigation workflow:

```text
Attack Performed
      ↓
Apache / Host Activity Generated
      ↓
Logs Collected
      ↓
Splunk Search
      ↓
Suspicious Events Identified
      ↓
Event Verification
```

This demonstrated how offensive security activity can be observed from a defensive monitoring perspective.

---

## Vulnerability Remediation

After completing the attack and detection phases, the identified vulnerabilities were reviewed and remediation measures were applied.

The remediation process followed this approach:

```text
Identify Vulnerable Code
        ↓
Understand Root Cause
        ↓
Apply Security Fix
        ↓
Restart / Update Service
        ↓
Retest Application
        ↓
Verify Vulnerability Is Mitigated
```

The goal was to demonstrate that security testing does not end after exploitation. Identified weaknesses should be understood, corrected, and tested again.

---

## Verification

After remediation, the affected functionality was tested again to verify that the previously successful attack technique was no longer effective or that its security impact had been appropriately mitigated.

This provided evidence of the transition from:

```text
Vulnerable State
      ↓
Attack Demonstration
      ↓
Detection
      ↓
Remediation
      ↓
Security Verification
```
